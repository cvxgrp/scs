BLAS and LAPACK

BLAS and LAPACK are dense numerical linear algebra packages. SCS uses these libraries in the following places:

  • To compute the eigen-decomposition for the semidefinite cone projection, and the eigen-decompositions and singular value decompositions for the spectral cones

  • To solve the linear system in Anderson acceleration

  • To form and factorize the matrix in the dense direct linear solver

  • To compute the eigenvectors that the indirect linear solver uses for deflation

  • For the basic vector operations (norms, inner products, scaling and adding vectors), which are plain C loops otherwise

Compiling with BLAS / LAPACK is optional: SCS builds and runs without them. A build without them cannot solve SDPs (the setup fails for a semidefinite cone larger than \(1 \times 1\)), cannot include the spectral cones or the parallel PSD projection, does not apply Anderson acceleration (whatever the value of acceleration_lookback), does not have the dense direct linear solver, and runs the indirect linear solver without deflation. If you need none of these then there is no need to use these libraries. To compile without these libraries you can set the compiler flag USE_LAPACK to 0, e.g., if installing using make:

make USE_LAPACK=0

If you do want any of the above, then you will need to install BLAS and LAPACK libraries (these are pre-installed in most machines). If calling SCS from another language (Python, MATLAB etc.) then these libraries should be pre-installed and SCS will try to link against them. Otherwise you may need to install a copy yourself. A good library to start with is OpenBLAS, which contains both BLAS and LAPACK.

There are many different BLAS and LAPACK libraries that conform to the same API. Finding one that is optimized for your machine can make a big difference to the speed of the operations in practice. If the speed of the SDP projection or the acceleration step is a bottleneck you can experiment with faster libraries like MKL or ATLAS.

Parallel projection of PSD blocks

A problem with several positive semidefinite (PSD) blocks spends much of its time projecting them, and SCS can project several blocks at the same time on different threads. It does so only in a build that asks for it, with the build option USE_PARALLEL_PSD. Without the option the blocks are projected one after another. That is the default, and it is how the Python wheels and the Julia packages are built.

The option is off by default because it is faster only with a BLAS that is set up for it, and slower with one that is not. This section explains when it helps, how to turn it on, and how to set up the BLAS.

When it helps

  • It helps with several PSD blocks of comparable size, many small ones or a few large ones. On 4 threads, 4 to 16 blocks of size 256 to 1024 were projected about 3 times faster, and a thousand blocks of size 10 to 32 about 3.5 times faster.

  • It does not help with one block, or one block much larger than the rest: a parallel projection is no faster than its largest block. SCS recognizes such a problem and projects its blocks one after another, as it does without the option.

  • It speeds up the projection, not the rest of a solve. If most of the time goes into the linear system, the solve as a whole gains little.

How to turn it on

Build SCS with OpenMP and with the option:

make USE_OPENMP=1 USE_PARALLEL_PSD=1

or, with CMake,

cmake -DUSE_OPENMP=ON -DUSE_PARALLEL_PSD=ON ..

With CMake the option takes effect only in the libraries that CMake compiles with OpenMP: scsdir, scsindir, scsdense, scsaccel and scsgpuindir. CMake compiles the MKL Pardiso and cuDSS libraries (scsmkl and scscudss) without OpenMP, so they project the blocks one after another whatever the option is set to. The Makefile compiles every library with OpenMP, these two included.

If CMake does not find OpenMP it prints the warning OpenMP requested but not found by CMake and builds every library without the parallel projection. The configure output still says Parallel PSD projection is ON, so check the header of a solve as described below.

For the Python package the option is use_parallel_psd, in an install from source: see the Python install page.

Then set the OpenMP thread count to the number of cores to use:

export OMP_NUM_THREADS=4

On a machine with fast and slow cores, count only the fast ones. Every thread gets an equal share of the blocks, so a thread on a slow core holds the others up.

Setting up the BLAS

Threads can work on the projection at two levels. SCS can project several blocks at once, and the BLAS can use several threads inside the eigendecomposition of a single block. Only one of the two should be active at a time. With the option on, every thread of SCS calls the BLAS, so the BLAS has to run on one thread there. If it does not, each thread of SCS starts the threads of the BLAS as well. There are then more threads than cores, and the projection is slower than it should be: in one measurement the process had 16 threads where 4 were asked for, and ran at half the speed.

Putting a BLAS on one thread with an environment variable holds for the whole process: that BLAS then runs on one thread wherever else it is used, in SCS (the dense linear solver) and in your own code. A BLAS on the OpenMP runtime of SCS has no such cost. The OpenMP thread count is then one budget, which SCS uses during a parallel projection and the BLAS uses everywhere else.

Checking that it works

  • With verbose set, the header of a solve says how many threads project the PSD blocks, for example psd cones projected in parallel by 4 threads. Without that line the blocks are projected one after another; the next part lists the reasons.

  • Count the threads of the process during a solve (top -H, or ps -o nlwp= -p <pid> on Linux). There should be about as many as the OpenMP thread count. Several times more means that the BLAS is running its own threads inside those of SCS.

  • Compare the time of a solve with that of a build without the option. If it is not faster, leave the option off.

How SCS uses the threads

The number of threads is fixed when the solver is set up. It is the OpenMP thread count at that point (as set by OMP_NUM_THREADS or omp_set_num_threads), at most the number of blocks larger than \(1 \times 1\). It is also bounded by the amount of work, because each thread takes a few microseconds to start. SCS counts 2 microseconds for each thread, and 5 on macOS (PSD_PAR_THREAD_COST in src/cones.c). The number of threads grows with about the square root of the time that SCS estimates for the projection on one thread. With many blocks of similar size, a projection of less than about 13 microseconds (32 on macOS) stays on one thread, one of 50 microseconds gets about 6 threads (4 on macOS), and one of a millisecond gets up to about 30 (20 on macOS). A solve uses fewer threads if the OpenMP thread count has been lowered since the setup.

Even with the option, the blocks are projected one after another, and the BLAS is free to use its own threads, when

  • the library was compiled without OpenMP (scsmkl and scscudss built with CMake, or any library if CMake did not find OpenMP),

  • the threads would gain little: the blocks are too little work, or one block holds most of it (the parallel projection is no faster than its largest block),

  • a block larger than \(512 \times 512\) holds more than half of the work (the parallel projection would then gain less than a factor of two, and a multithreaded BLAS may do better on that block),

  • the BLAS is a pthreads build of OpenBLAS set to more than one thread, where SCS can see that (see below), or

  • the solver is set up inside an active OpenMP parallel region, where the threads of the caller are the parallelism.

The number of threads is chosen as if the threads were awake when a projection starts. With the GNU OpenMP runtime on Linux they wait actively for a short time after a parallel region (GOMP_SPINCOUNT) and then sleep, and waking them can cost more than a small projection gains. On one machine, PSD blocks that took less than a millisecond in all made an iteration up to 27% slower when the rest of the iteration took a millisecond or more. If the PSD blocks are a small part of a large problem, a build without USE_PARALLEL_PSD suits it better. OMP_WAIT_POLICY=active keeps the threads awake between projections, at the price of cores that are busy while they wait.

What SCS checks, and where it cannot

SCS guards against two of the cases in the table, on some platforms only. That is the reason the option is left to whoever builds SCS and knows its BLAS.

  • MKL on another OpenMP runtime: SCS sets the thread-local thread count of MKL to one during the projection. This goes through a weak reference to MKL_Set_Num_Threads_Local, which needs an ELF platform such as Linux and the MKL symbols visible to SCS. It does not work on Windows or macOS, with a static MKL, or with an MKL loaded privately by another library.

  • A pthreads build of OpenBLAS with more than one thread: on ELF platforms SCS checks for it at setup and then projects the blocks one after another. With OPENBLAS_NUM_THREADS=1 the projection is parallel, but the BLAS calls of the threads still wait for one lock inside an OpenBLAS that was not built with OpenMP. SCS counts that when it chooses the number of threads: small blocks mostly stay serial, and blocks of \(10 \times 10\) to \(32 \times 32\) get two to six threads. An OpenMP build of OpenBLAS does not have this limit. Both checks need the functions openblas_get_parallel and openblas_get_num_threads visible to SCS: they are off for a static libopenblas.a (the weak references can stay unresolved), for an OpenBLAS with suffixed symbol names, and for one loaded privately by another library (libblastrampoline in Julia).

  • In all other cases (other platforms, other libraries, another OpenMP runtime) SCS does nothing and assumes that the BLAS runs on one thread.

Thread safety, memory and reproducibility

Several threads call BLAS and LAPACK at once, so the library must be safe to call that way. A single-threaded OpenBLAS (built with USE_THREAD=0) is safe only if it was built with USE_LOCKING=1 (see OpenBLAS’s Makefile.rule). SCS does not check this; OpenBLAS 0.3.28 and later list USE_LOCKING in openblas_get_config(). OpenBLAS also has a table of memory buffers of a size fixed when it is built (by NUM_THREADS, and at least 50), and a thread holds one during a BLAS call: with more threads than buffers, OpenBLAS 0.3.18 and later print a warning and allocate more, and earlier versions fail. The OpenMP thread count bounds the number of threads.

A parallel projection takes more memory: each thread after the first has its own eigendecomposition workspace, with matrix buffers for the largest block that thread projects and LAPACK work arrays of the serial sizes. The extra memory is therefore at most the PSD workspace of the serial projection times the number of threads less one. That workspace is about \(2n^2\) floats for the largest real block of size \(n\) and \(2n^2\) complex numbers for the largest complex block, plus LAPACK work arrays linear in \(n\).

Each block goes through the same LAPACK calls as in the serial projection, so with single-threaded BLAS the result is the same bit for bit, whatever the number of threads (unless the rounding of the BLAS depends on the memory alignment of its arguments, as it can with MKL).
