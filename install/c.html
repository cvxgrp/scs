C / C++

First clone the SCS repo from GitHub

git clone https://github.com/cvxgrp/scs.git

CMake

Thanks to the CMake buildsystem SCS can be easily compiled and linked to other CMake projects. To use the cmake build system please run the following commands:

cd scs
mkdir build
cd build
cmake -DCMAKE_INSTALL_PREFIX:PATH=<custom-folder> ../
make
make install

You may also want to compile the tests. In this case when you configure the project, please call the following command

cmake -DCMAKE_INSTALL_PREFIX:PATH=<custom-folder> -DBUILD_TESTING=ON ../
make
ctest

Some compile flags can be overridden using the command line, for example we can compile the library (and headers) to use 64 bit integers using:

cmake -DCMAKE_INSTALL_PREFIX:PATH=<custom-folder> -DDLONG=ON ../
make

By default the build-system will compile the library as shared. If you want to compile it as static, please call the following command when you configure the project

cmake -DCMAKE_INSTALL_PREFIX:PATH=<custom-folder> -DBUILD_SHARED_LIBS=OFF ../
make

The CMake build-system exports two CMake targets called scs::scsdir and scs::scsindir as well as a header file scs.h that defines the API (installed with the two headers it includes, scs_types.h and aa_stats.h). When LAPACK is available (the default), it also exports scs::scsdense for the dense direct solver.

MKL

If MKL is installed in your system and the MKLROOT environment variable is set, then additionally CMake will build and install the MKL Pardiso linear solver with target scs::scsmkl. CMake finds MKL through the CMake package that oneMKL installs (MKLConfig.cmake, oneMKL 2021.3 or later), which it looks for under MKLROOT. Configuration stops with an error if that package is not found. SCS links the single dynamic library (mkl_rt) through the MKL::MKL target of that package, so there is no MKL link line to edit in the CMake build.

Setting MKLROOT also changes the BLAS/LAPACK of the other SCS libraries. When USE_LAPACK is on (the default), CMake then looks for MKL as the BLAS/LAPACK library (it sets BLA_VENDOR to Intel10_64lp, or to Intel10_64ilp with BLAS64=ON), and every SCS library that links the BLAS/LAPACK found by CMake links against it, scs::scsdir, scs::scsindir and scs::scsdense among them. To keep another BLAS/LAPACK for those libraries, pass BLA_VENDOR on the command line, e.g. -DBLA_VENDOR=OpenBLAS.

The BLAS64 compile flag is a general SCS flag for ILP64 BLAS/LAPACK libraries. When using the MKL Pardiso backend specifically, BLAS64=1 must be paired with DLONG=1 so that pardiso_64 matches the 64-bit BLAS interface. In the CMake build, BLAS64=ON also requires that CMake can find an ILP64 BLAS/LAPACK implementation; if autodetection needs help, set BLA_VENDOR explicitly.

GPU

If you have a GPU and the CUDA toolkit installed, you can build the GPU indirect solver:

cmake -DCMAKE_INSTALL_PREFIX:PATH=<custom-folder> -DUSE_GPU=ON ../
make

This builds and installs the GPU solver with target scs::scsgpuindir. CMake locates the CUDA runtime, cuBLAS and cuSPARSE with FindCUDAToolkit, which honors CUDAToolkit_ROOT if the toolkit lives somewhere unusual. Build it with 32 bit integers, that is with DLONG left off (the default). The solver passes its integers to cuBLAS and cuSPARSE routines that take 32 bit ones, and CMake does not check this: with -DDLONG=ON the build either fails or, with a compiler that only warns about the mismatched pointer types, produces a solver that does not work. The transpose of A is stored in GPU memory by default; configure with -DGPU_TRANSPOSE_MAT=OFF to save that memory at the cost of slower products with A.

If the tests are enabled as well (-DBUILD_TESTING=ON), the test program run_tests_gpu_indirect is built and registered with CTest. It builds wherever the CUDA toolkit is installed, but it needs a GPU to run. On a machine without one (a packaging machine, for instance) leave it out with

ctest -E gpu

Note that the GPU is typically only faster than the CPU for very large problems, and that the indirect solver is a legacy backend: the cuDSS direct solver described below is the recommended GPU backend and should be preferred whenever cuDSS is available.

cuDSS

If you have a GPU and CUDA toolkit installed, along with the cuDSS library, you can compile SCS with cuDSS support using CMake. CMake locates the CUDA toolkit with FindCUDAToolkit, as for the GPU indirect solver above, and cuDSS through the CMake package that cuDSS itself installs (find_package(cudss)), so nothing needs to be set when both are in standard locations. If cuDSS is somewhere else, pass its install prefix with -DCMAKE_PREFIX_PATH=<cudss-prefix>, or the folder that holds its CMake package files (cudss-config.cmake) with -Dcudss_DIR=<folder>. The CUDSS_PATH variable is only used by the Makefile build and has no effect here. Then configure with cuDSS enabled:

cmake -DCMAKE_INSTALL_PREFIX:PATH=<custom-folder> -DUSE_CUDSS=ON -DDLONG=OFF ../
make

The CMake build of the cuDSS solver only accepts 32 bit integers (for sparse matrix indices), so -DDLONG=OFF (the default) is mandatory: configuring with -DDLONG=ON is an error. This will build and install the cuDSS linear solver with target scs::scscudss.

With -DBUILD_TESTING=ON the test program run_tests_cudss is registered with CTest in the same way as the GPU indirect one, and it also needs a GPU to run. On a machine without one leave it out with ctest -E cudss (or ctest -E 'gpu|cudss' if both GPU solvers were built).

Importing

The libraries can be imported using the find_package CMake command and used by calling target_link_libraries as in the following example. SCS needs CMake 3.22 or newer to build, and a static SCS package (-DBUILD_SHARED_LIBS=OFF) cannot be imported by an older CMake. Link the target for the linear solver you want: scs::scsdir and scs::scsindir are always installed, the others only when SCS was built with that solver.

cmake_minimum_required(VERSION 3.22)
project(myproject)
find_package(scs REQUIRED)
add_executable(example example.cpp)

# To use the direct method
target_link_libraries(example scs::scsdir)

# To use the indirect method
target_link_libraries(example scs::scsindir)

# To use the MKL Pardiso direct method
target_link_libraries(example scs::scsmkl)

# To use the dense direct method (requires LAPACK)
target_link_libraries(example scs::scsdense)

# To use the cuDSS direct method
target_link_libraries(example scs::scscudss)

# To use the GPU indirect method (requires -DUSE_GPU=ON)
target_link_libraries(example scs::scsgpuindir)

# To use the Apple Accelerate direct method (macOS only, requires
# -DUSE_APPLE_ACCELERATE=ON)
target_link_libraries(example scs::scsaccel)

Makefile

Alternatively you can use the Makefile and manage the libraries and header files yourself. The public header files are scs.h, scs_types.h and aa_stats.h. Your code only needs to include scs.h, but scs.h includes the other two, so all three must be on the include path.

cd scs
make

To compile and run the tests execute

make test
out/run_tests_direct
out/run_tests_indirect

If make completes successfully, it will produce two static library files, libscsdir.a, libscsindir.a, and two dynamic library files libscsdir.ext, libscsindir.ext (where .ext extension is platform dependent) in the out folder.

If MKL is installed in your system and the MKLROOT environment variable is set, then you can compile and test the MKL Pardiso version of SCS using:

make mkl
out/run_tests_mkl

This will produce static library libscsmkl.a and dynamic library libscsmkl.ext (again .ext is platform dependent) in the out folder. The MKL link line (MKLFLAGS in scs.mk) is written for Linux with GCC and may need to be modified for your system. It links Intel’s OpenMP library (libiomp5), which it looks for in the lib folder of OMPROOT. OMPROOT defaults to MKLROOT. If libiomp5 is somewhere else, as in a oneAPI installation, set OMPROOT, e.g. make mkl OMPROOT=/opt/intel/oneapi/compiler/latest.

If you want 64-bit BLAS/LAPACK integers with the MKL Pardiso backend, build with both BLAS64=1 and DLONG=1.

To compile and test the dense direct solver (requires LAPACK):

make dense
out/run_tests_dense

This will produce static library libscsdense.a and dynamic library libscsdense.ext (where .ext is platform dependent) in the out folder. The dense solver is best suited for small to medium-sized problems.

If you have a GPU and have CUDA installed, you can also execute make gpu to compile SCS to run on the GPU which will create additional libraries and demo binaries in the out folder corresponding to the GPU version. Unlike the other targets, make gpu does not build the test program, which has its own target make test_gpu. The Makefile looks for the CUDA toolkit in /usr/local/cuda; set CUDA_PATH if it is somewhere else. The GPU indirect solver requires 32 bit integers, which is the default (DLONG=0): make gpu DLONG=1 does not compile.

make gpu
make test_gpu
out/run_tests_gpu_indirect

The GPU sources are compiled by the host C compiler rather than by nvcc, so they include the CUDA headers directly. This means the crt headers must be present alongside the runtime: up to CUDA 12 they were part of the cuda_nvcc component, whereas CUDA 13 moved them into a separate cuda_crt component. A partial installation that omits it fails with

driver_types.h:59:30: fatal error: crt/host_defines.h: No such file or directory

Installing the full CUDA toolkit pulls the component in automatically; only builds that pick individual components (distribution packaging, for instance) need to request it explicitly.

Finally, to compile and test the cuDSS solver you need to have CUDA toolkit, the nvcc compiler, and cuDSS library installed. Then set CUDA_PATH and CUDSS_PATH and execute

make cudss
out/run_tests_cudss

The default is 32 bit integers (DLONG=0). The Makefile build also accepts make cudss DLONG=1, in which case SCS passes 64 bit sparse matrix indices to cuDSS (see the docs of cuDSS CSR matrix). That build passes the tests on a GPU with cuDSS 1.0; it has not been run against older cuDSS releases. The CMake build only accepts 32 bit integers.

To use the libraries in your own source code, compile your code with the linker option -L(PATH_TO_SCS_LIBS) and -lscsdir or -lscsindir (as needed). The API and required data structures are defined in the file include/scs.h and documented here.
