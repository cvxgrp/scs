Linear System Solver

At each iteration \(k\) SCS solves the following set of linear equations:

\[\begin{split}\begin{bmatrix} R_x + P & A^\top \\ A & -R_y \\ \end{bmatrix} \begin{bmatrix} x \\ y \end{bmatrix} = \begin{bmatrix} z^k_x \\ z^k_y \end{bmatrix}\end{split}\]

for a particular right-hand side \(z^k \in \mathbf{R}^{n+m}\). The presence of the diagonal scaling \(R \in \mathbf{R}^{(n+m) \times (n+m)}\) matrix is explained in Non-identity DR Scaling. The \(R_y\) term is negated to make the matrix quasi-definite; we can recover the solution to the original problem from this modified one. Note that the matrix does not change from iteration to iteration, which is a major advantage of this approach. Moreover, this system can be solved approximately so long as the errors satisfy a summability condition, which permits the use of approximate solvers that can scale to very large problems.

One solve is treated differently. At the start of every solve, and whenever the scaling \(R\) changes, SCS solves the system once for the right-hand side \((c, -b)\) and uses that solution in every iteration until the next change, so an error in it is repeated in every iteration rather than averaged out. SCS therefore checks that solve, whatever the linear solver: it computes the residual from the problem data and, while the residual is larger than \(10^{-12}\) relative to the size of the terms (\(10^{-5}\) in single precision), it refines the solution by solving for the residual, for at most three steps. This costs one multiply by the matrix each time, plus one solve and one multiply per refinement step; with the indirect solvers a refinement step is another conjugate gradient solve.

Accuracy of each iteration’s solve

SCS’s residuals cannot become much smaller than the error of the linear-system solve in each iteration, so SCS checks that error and makes the solves more accurate when it would limit the iterates. Nothing needs to be set for this.

The check. Every 25 iterations SCS computes the residual of that iteration’s solve, \(\|z^k - K u\|_\infty\) with \(K\) the matrix above, and compares it with tol, the smaller of SCS’s own primal and dual residuals at its last convergence check (but at least \(10^{-12}\), \(10^{-5}\) in single precision). The check costs one multiply by \(K\) every 25 iterations.

Direct solvers (sparse direct, dense, Apple Accelerate, MKL Pardiso, cuDSS). When the residual of a check is above \(0.01\,\) tol, each following iteration solves in correction form: from the previous iteration’s solution \(u_0\) it solves \(K d = z^k - K u_0\) and takes \(u = u_0 + d\). The error of a solve with a factorization is about proportional to the size of the right-hand side it is given. The iterates move little from one iteration to the next, so \(z^k - K u_0\) is \(10^{-3}\) to \(10^{-7}\) of \(z^k\), and \(u\) is that much more accurate than a plain solve, for one more multiply by \(K\) per iteration and no extra solve. The errors do not build up from one iteration to the next: each correction-form solve shrinks the error it inherits by the same factor as it shrinks the right-hand side. When the previous solution is no better a guess than zero (\(\|z^k - K u_0\| \ge \|z^k\|\), which happens after \(R\) changes) that iteration solves plainly. At each check while it is on, SCS also makes a plain solve of the same right-hand side, only to measure its error, and turns the correction form off once that error is at most \(0.001\,\) tol; the iterate stays the correction-form solution, unless the correction-form solution’s own residual (one more multiply by \(K\) per check) is more than twice the plain solve’s and above rounding level (\(10^{-14}\,\|z^k\|_\infty\) in double precision, \(10^{-5}\,\|z^k\|_\infty\) in single). That safeguard is for a factorization so inaccurate that the correction form does not reduce the error; normally the correction-form residual is near rounding level and the safeguard changes nothing.

Why these choices: what slows SCS down is switching between accurate and inexact solves, more than the inexact solves themselves. On QFORPLAN at \(10^{-6}\) with Apple Accelerate, the previous rule (refine only once the error exceeds tol, with one more solve per iteration, until it falls below \(0.1\,\) tol) took 1,300 to 140,900 iterations depending on the starting point, and the correction form with the plain solve put into the iterate at every check (one inexact solve every 25 accurate ones) took up to 31 times the iterations of the rule here, which took 700 to 975. Turning on at \(0.01\,\) tol and off at \(0.001\,\) tol starts the accurate solves before they are needed and keeps them while the residuals fall. Thresholds ten times lower were on for 12.6% of the iterations at the default tolerances instead of 1.3%, and for most of the solve on more problems, with similar results at tight tolerances; ten times higher ones took more iterations on the badly scaled problems.

Indirect solvers (CPU and GPU conjugate gradients). Conjugate gradients already solves to a tolerance tied to SCS’s residuals, and its error is set by that tolerance rather than by the size of the right-hand side, so the correction form would not make it more accurate. When a check finds the residual above tol, each following iteration’s solve is followed by one refinement step (one more multiply and one more conjugate gradient solve, for the residual), until a check finds it at most \(0.1\,\) tol. This fires only when a conjugate gradient solve misses its tolerance.

What to expect (direct solvers):

  • At the default tolerances it rarely turns on: on 112 LPs, QPs and SDPs at \(10^{-4}\) and \(10^{-6}\) from 3 starting points each (QDLDL), for 1.3% of the iterations, with the same iterations in 318 of the 336 runs (9 fewer, 9 more) and about 1% more time, within the run-to-run noise.

  • At tight tolerances it is what lets direct solves converge, and it takes fewer iterations than refining once the error is already too large: on 500 random LPs and SOCPs at \(10^{-9}\) with QDLDL, 2.6% fewer iterations and 2.3% less time; with cuDSS on 200 of them, 7% fewer iterations and 9% less solve time (14% less without Anderson acceleration); with Apple Accelerate, whose solves can be inaccurate on badly scaled problems, on 30 LPs, QPs and SDPs at \(10^{-4}\) and \(10^{-6}\) from 3 starting points each, 0.95 times the time in geometric mean of the per-run ratios, and 0.89 times the shifted geometric mean of the times (shift 10 s), which weighs the long runs more (QFORPLAN at \(10^{-6}\): 700 to 975 iterations, where the previous rule took 1,300 to 140,900 depending on the starting point). On 45 LPs and QPs at \(10^{-8}\) and \(10^{-9}\) with QDLDL the results were the same within noise. MKL Pardiso’s solves are accurate enough that it turns on less often: on 33 LPs and QPs at \(10^{-9}\), in 15 of them, for 3.5% fewer iterations and the same time.

  • While it is on, an iteration’s linear-system time is about 1.1 to 1.5 times that of a plain one: the extra multiply by \(K\) costs most, relative to the solve, on small and very sparse systems (1.4 with QDLDL on small LPs, 1.1 with Accelerate on larger QPs).

  • On a problem that stalls it can stay on for most of the remaining iterations: on 26 SDPs and QPs that stall at \(10^{-4}\) to \(10^{-6}\) (78 runs), it was on for 19% of the iterations and for most of the solve in 11 runs, which solved one run more and took 6% more time. In single precision it tends to stay on once it turns on, because the threshold to turn it off is near or below what a single-precision solve can reach.

Who computes the multiplies. By default SCS computes the multiplies by \(K\) itself, from the problem data, on one thread. A linear solver can compute them with its own copy of \(K\) instead (see Implementing a new linear solver): MKL Pardiso uses MKL’s threaded sparse matrix-vector product, and cuDSS computes them on the GPU, where the vectors stay. The decisions above are the same either way; only the cost of the multiply and its rounding change.

What the solver’s own multiplies buy is a cheaper iteration while the correction form is on. With cuDSS on 10 large LPs, QPs and SOCPs at \(10^{-8}\) (NVIDIA GB10), such an iteration cost 1.19 times a plain one with the multiplies on the GPU, against 1.48 with SCS’s on the CPU (on BOYD1 1.61 ms against 2.63, a plain iteration taking 1.33). With MKL Pardiso on 33 LPs and QPs at \(10^{-9}\) (4 threads, AMD Zen 3) it cost 1.32 times a plain one against 1.45. Whole solves changed by a few percent at most, within the run-to-run variation of the iteration counts, because the correction form is on for a small part of most solves.

Available linear solvers

Each of the below linear solvers is included in their own binary. If linking against SCS directly, then to switch between them you must compile and link against the right binary. If calling SCS via one of the interfaces then you can choose between the different linear solvers using the appropriate settings.

Sparse direct

The direct method is the default linear system solver in SCS and factorizes the above matrix using a sparse permuted LDL factorization. Then it solves the linear system at each iteration using the cached factors. Since the linear system is quasidefinite we have strong existence guarantees about the factorization. It relies on the external (but included) AMD and QDLDL packages.

Dense direct

The dense direct method reduces the KKT system to the smaller Gram matrix \(G = R_x + P + A^\top R_y^{-1} A\) (size \(n \times n\)) and factorizes it using the LAPACK dpotrf (Cholesky) routine. The \(A^\top R_y^{-1} A\) product is computed via dsyrk and subsequent solves use dpotrs. When the diagonal \(R\) changes, the Gram matrix is re-formed and re-factorized.

This backend is best suited for small to medium-sized problems where the constraint matrix \(A\) is dense. For such problems, dense BLAS/LAPACK routines can outperform sparse solvers due to highly optimized memory access patterns and lower overhead. It requires LAPACK (USE_LAPACK=1).

MKL Pardiso

The Intel MKL Pardiso solver is a shared-memory multiprocessing parallel direct sparse solver which is included Intel oneAPI MKL library. This offers an alternative to the single threaded AMD / QDLDL libraries which come bundled with SCS. Pardiso tends to be faster than AMD / QDLDL, especially for larger problems. If MKL is installed on your system then it is generally worth using MKL for both the blas / lapack usage as well as the linear system solve. Intel MKL is now available for free and without restrictions for everyone, though it only offers limited support for non-Intel CPUs. The x86-64 manylinux Python wheels include it, statically linked (see Python).

Threads. With a threaded MKL, Pardiso runs on MKL’s threads (MKL_NUM_THREADS, else OMP_NUM_THREADS): the reordering, the factorization and the solve done in every iteration, which SCS asks Pardiso to run in parallel. Starting and synchronizing the threads costs a few tens of microseconds per call, which on a small linear system is more than the work. So SCS runs Pardiso on one thread when the factor Pardiso computes has fewer than 50,000 nonzeros (PARDISO_MIN_THREADED_NNZ in linsys/mkl/direct/private.c). The choice is made once, at setup, from the problem data and the ordering Pardiso computes; all the Pardiso calls of a solve then use the same thread count, and MKL’s BLAS and LAPACK keep their threads. On 4 threads, small problems iterated up to about 2x faster this way with MKL_DYNAMIC=FALSE, and up to about 1.3x with MKL’s default (dynamic mode, which already runs the smallest systems on one thread by itself); larger ones were unaffected. The break-even point depends on the problem and the machine; in our measurements it was between about 30,000 and 60,000 factor nonzeros. A sequential MKL, such as the one in the Python wheels, always runs on one thread, so there this changes nothing. On small problems a sequential MKL is still faster than a threaded one, because a threaded MKL costs more per call even on one thread. On several threads Pardiso may round differently from run to run, so two runs of the same problem can differ slightly in their results and iteration counts.

Multiplies for the refinement. MKL Pardiso computes the multiplies by \(K\) of the per-iteration refinement (see Accuracy of each iteration’s solve) with MKL’s sparse BLAS, on the same upper triangle Pardiso factorizes, analysed once at setup (mkl_sparse_optimize). They run on MKL’s threads, or on one thread when Pardiso does (the rule above), so that a solve never mixes thread counts. Measured per multiply against SCS’s own single-threaded product (AMD Zen 3, 4 threads, 46 LPs and QPs): 0.2 to 0.5 times the time where it runs on MKL’s threads (0.76 against 2.39 ms on co-100), and 0.45 to 0.93 times where it runs on one thread; forcing 4 threads on the smallest systems made it about twice as slow as one thread. In the solves, an iteration with the correction form on cost 1.32 times a plain one, against 1.45 with SCS’s product (33 LPs and QPs at \(10^{-9}\)). The products add no run-to-run variation of their own: with the same number of threads they gave the same bits in repeated runs (a different thread count can change their last bits). The products also cost setup time that has not been measured: MKL analyses \(K\) (mkl_sparse_optimize) at setup and again at every update of \(R\), whether or not the correction form ever turns on, since the check every 25 iterations uses the product too. In a build with DLONG but 32-bit MKL integers, a \(K\) too large for those integers (more than \(2^{31}\) stored nonzeros) gets SCS’s own products instead, as before this change; BLAS64=1 (Meson’s use_blas64) provides MKL’s at any size. If they cannot be set up otherwise (out of memory), setup fails with a message.

Apple Accelerate

The Apple Accelerate framework provides a sparse LDLT factorization that is optimized for Apple hardware (including Apple Silicon). This backend uses the unpivoted LDLT solver from the Accelerate Sparse Solvers API, which is well-suited for the quasi-definite KKT systems that SCS produces. Accelerate performs its own fill-reducing ordering internally so no external AMD package is needed.

This backend is macOS-only and is available without installing any additional libraries since the Accelerate framework ships with Xcode / the macOS SDK. It does not support 64-bit integer indexing (DLONG).

To build with Make:

make accelerate

To build with CMake:

cmake -DUSE_APPLE_ACCELERATE=ON ..

In Python, the Accelerate backend is included automatically on macOS (pip install scs is sufficient). On macOS, linear_solver=scs.LinearSolver.AUTO selects the bundled QDLDL; select Accelerate explicitly with:

solver = scs.SCS(data, cone, linear_solver=scs.LinearSolver.ACCELERATE)

Sparse indirect

The indirect method solves the above linear system approximately with a ‘matrix-free’ method. To do this it first reduces the system to solving

\[\begin{split}(R_x + P + A^\top R_y^{-1} A) x & = z^k_x + A^\top R_y^{-1} z^k_y \\ y & = R_y^{-1}(A x - z^k_y).\end{split}\]

then solves the positive definite system using using conjugate gradients. Each iteration of CG requires one multiply each of sparse matrices \(P, A, A^\top\). The system is solved up to some tolerance, which is tuned to ensure that the overall algorithm converges: each solve targets a small fraction (CG_TOL_FACTOR, default \(0.03\)) of the smaller of the current primal and dual residuals, additionally capped by a term decaying with iteration \(k\) like \(O(1/k^\gamma)\) where \(\gamma\) is determined by the constant CG_RATE (defaults to \(2\)), and floored at CG_BEST_TOL. Each solve is warm-started from the previous solution. The solver also harvests approximate eigenvectors of the reduced matrix from the CG iterations themselves (eigCG; Stathopoulos and Orginos 2010) and uses up to DEFLATE_VECTORS (default 30) of them to deflate the smallest eigenvalues from subsequent solves, which substantially reduces the CG iterations needed on ill-conditioned problems. Applying the deflation in a solve costs no matrix multiplies. Each harvest costs the multiplies of one CG iteration per vector.

Deflation needs LAPACK and double precision. It is switched off when SCS is built without LAPACK (USE_LAPACK=0) or in single precision (SFLOAT=1), and only the CPU indirect solver has it. Single precision builds also use \(0.2\) for CG_TOL_FACTOR and \(1.5\) for CG_RATE.

Deflation keeps \(2n\) numbers per vector in memory (\(60n\) by default), and a harvest takes a further \(n\) numbers per window entry and \(2n\) per vector while it runs (\(150n\) by default). Two environment variables change this for a run without recompiling. Both are read once, when the solver is set up (scs_init):

  • SCS_DEFLATE sets the number of deflation vectors in place of DEFLATE_VECTORS. SCS_DEFLATE=0 turns deflation off.

  • SCS_EIGCG_WIN sets the size of the eigCG window, the number of CG vectors that a harvest keeps in memory (default 60, EIGCG_WINDOW in linsys/cpu/indirect/private.c). The window is never smaller than three times the number of deflation vectors, so with the default 30 vectors it is 90 and a smaller SCS_EIGCG_WIN has no effect unless SCS_DEFLATE is lowered as well.

The indirect method has the advantage of not requiring an expensive factorization but typically is slower on a per-iteration basis. In most cases the factorization is relatively cheap so the direct method is the default, however for very large problems the indirect solver can be faster.

Sparse GPU indirect method

The above linear solvers all run on CPU. We also have support for a GPU version of the indirect solver, where the matrix multiplies are all performed on the GPU. It runs conjugate gradients with the same diagonal preconditioner, tolerance schedule and warm start as the CPU indirect solver, but it does not harvest eigenvectors or deflate, so DEFLATE_VECTORS and the SCS_DEFLATE and SCS_EIGCG_WIN environment variables have no effect on it. Usually the direct GPU solver will be faster than this solver.

Sparse GPU direct method

This is a linear solver that uses the cuDSS library to solve the linear system on the GPU. It is similar to the direct solver, but uses the calls to cuDSS library to perform the analysis, numerical (re-)factorization and subsequent solves. According to its documentation reordering (a major part of the analysis phase) is executed on the host while symbolic factorization (another part of the analysis phase), numerical factorization, and solve are executed on the GPU.

SCS runs cuDSS without pivoting, matching or iterative refinement, so it computes a plain LDL’ factorization, as the CPU direct solver does. The linear system is quasi-definite, so this factorization exists under any ordering, and each iteration costs one solve. From version 1.0, cuDSS by default applies a matching to a symmetric indefinite matrix. With its default pivoting that makes the factorization up to four times larger (2.4 times larger on average on the LPs and QPs measured), and without pivoting it made the solves inaccurate enough for SCS to stall on some LPs. Older versions of cuDSS do not apply a matching unless asked to, so SCS factorizes the same way with every cuDSS version it supports. The tradeoff is that the accuracy of a solve rests on the conditioning of the system: the worst relative residual of a solve in the test suite was about 6e-8, against 5e-11 with cuDSS’s default pivoting and matching. Single-precision builds keep one step of iterative refinement per solve, which about doubles the cost of a solve, because without it one problem in the test suite does not converge.

Multiplies for the refinement. When \(K\) has at least 60,000 nonzeros (CUDSS_MIN_PRODUCT_NNZ in linsys/cudss/direct/private.c), the cuDSS solver computes the multiplies by \(K\) of the per-iteration refinement (see Accuracy of each iteration’s solve) on the GPU: one cuSPARSE sparse matrix-vector product and one cuBLAS reduction, with the guess and the residual kept on the GPU, so an iteration in correction form copies no more vectors between the host and the GPU than a plain solve. cuSPARSE has no symmetric product, so \(K\) is stored a second time with both triangles, about twice the nonzeros of the copy cuDSS factorizes. A call costs about 0.04 ms whatever the size, so smaller systems use SCS’s product on the CPU, which was faster there. On an NVIDIA GB10, per multiply, the GPU took 0.12 to 0.37 times the CPU’s time above \(3.7 \cdot 10^5\) nonzeros (0.18 against 1.27 ms on BOYD1). In the solves, on 10 large LPs, QPs and SOCPs at \(10^{-8}\), an iteration with the correction form on cost 1.19 times a plain one, against 1.48 with the multiplies on the CPU, and the time per iteration fell by 4%. Setting them up (building \(K\) with both triangles, copying it to the GPU, creating the cuSPARSE and cuBLAS handles) is done at setup whether or not the correction form ever turns on, since the check every 25 iterations uses the multiply too. On the GB10 it took 3, 35 and 340 ms for random \(K\) with \(10^5\), \(10^6\) and \(8 \cdot 10^6\) nonzeros, 5 to 13% of the time cuDSS’s own setup (analysis and factorization) took; the two handles took 0.4 to 0.8 ms of that. If they cannot be set up (out of GPU memory, or a \(K\) too large for 32-bit indices in a build without DLONG), setup fails with a message.

Reproducibility of the GPU solvers

With either GPU solver, two runs of the same problem on the same machine are not guaranteed to give bit for bit the same result. The GPU indirect solver does its sparse matrix-vector products with cuSPARSE’s CUSPARSE_SPMV_CSR_ALG1, which cuSPARSE does not guarantee to give the same bits on every run, and SCS runs cuDSS without its deterministic mode (CUDSS_CONFIG_DETERMINISTIC_MODE), which made LPs and QPs several times slower to solve on an NVIDIA GB10. SCS has no setting to change either choice. The multiplies of the refinement on the GPU (cuDSS, see above) use CUSPARSE_SPMV_CSR_ALG2, which gives the same result every run, so they add no variation of their own. When two runs differ, their iterates differ slightly. Printed values that are small near the end of a solve, such as the dual residual and the gap, can then differ in every digit, and the iteration count can change if a residual ends close to its tolerance. In a check on an NVIDIA GB10 (CUDA 13.0, cuDSS 1.0.0), three runs of a random SOCP with each GPU solver all took 150 iterations, and their last iterations differed in the dual residual and the gap (the gap of the GPU indirect solver by a factor of 13).

Implementing a new linear solver

In order to implement you own linear system solver, you need to implement the struct ScsLinSysWork that contains the workspace your solver requires, and implement the functions in include/linsys.h as detailed below. See linsys directory for examples.

Products with the matrix (optional). The per-iteration refinement of the direct solvers (see Accuracy of each iteration’s solve) multiplies by the matrix \(K\): every 25 iterations to check a solve, and once per iteration while the correction form is on. By default SCS computes these products itself, from the problem data, on one thread. A solver that holds \(K\) anyway can compute them faster with its own copy, by implementing three functions:

  • scs_lin_sys_residual(w, b, x) computes \(r = b - K x\) with the solver’s current \(K\) (including the latest \(R\) from scs_update_lin_sys_diag_r), keeps \(r\), and returns \(\|r\|_\infty\). If x is SCS_NULL, \(x\) is the vector stored by the last scs_lin_sys_keep.

  • scs_lin_sys_keep(w, x) stores \(x\) as the guess \(x_0\). SCS calls it with the solution of the latest solve (a scs_solve_lin_sys or scs_lin_sys_correct call), unchanged, so a GPU solver can copy the solution it still has on the device and not read x at all. Between that solve and this call SCS may call scs_lin_sys_residual (when it turns the correction form on, it checks the solve with scs_lin_sys_residual(w, b, x) first), but no other solve, so the residual must not overwrite the solver’s copy of the solution.

  • scs_lin_sys_correct(w, x) returns \(x = x_0 + K^{-1} r\) for the \(r\) of the latest scs_lin_sys_residual(w, b, SCS_NULL).

Every solver must define the three functions so that it links (an out-of-tree solver written for an earlier SCS needs the three stubs below). The contract:

  • scs_lin_sys_residual returns \(\|r\|_\infty \ge 0\), SCS_LIN_SYS_PRODUCTS_NOT_PROVIDED if the workspace does not compute the products, or SCS_LIN_SYS_PRODUCTS_FAILED on an error.

  • Whether a workspace provides the products is fixed when scs_init_lin_sys_work returns, by a rule stated up front (cuDSS: the number of nonzeros of \(K\); MKL Pardiso: always, except a \(K\) too large for 32-bit MKL integers in a DLONG build without BLAS64), never by whether memory or a library happened to be available. A solver that should provide them but cannot set them up makes scs_init_lin_sys_work fail with a message saying why, rather than returning “not provided”.

  • SCS calls scs_lin_sys_residual once at setup, with zero vectors: “not provided” makes SCS compute every product itself (and never call the other two functions); a failure makes SCS’s setup fail; a norm means the solver provides them. During a solve any negative return is a failure of the linear solver.

A solver without the products defines:

scs_float scs_lin_sys_residual(ScsLinSysWork *w, const scs_float *b,
                               const scs_float *x) {
  return SCS_LIN_SYS_PRODUCTS_NOT_PROVIDED;
}
void scs_lin_sys_keep(ScsLinSysWork *w, const scs_float *x) {}
scs_int scs_lin_sys_correct(ScsLinSysWork *w, scs_float *x) { return -1; }

SCS makes every decision (when to check, the thresholds, when to use the guess); the solver only computes, so the refinement behaves the same with every solver, up to the rounding of the product. test_lin_sys_products in the test suite checks a solver’s products against SCS’s own. The MKL Pardiso solver (linsys/mkl/direct/private.c, with MKL’s sparse BLAS) and the cuDSS solver (linsys/cudss/direct/private.c, on the GPU with cuSPARSE and cuBLAS) are examples; the other solvers return “not provided”.

scs_float scs_lin_sys_residual(ScsLinSysWork *w, const scs_float *b, const scs_float *x)

Computes \(r = b - K x\) with the solver’s own copy of K (as updated by the last scs_update_lin_sys_diag_r) and returns \(\|r\|_\infty\). The solver keeps r for a following scs_lin_sys_correct. If x is SCS_NULL, x is the vector stored by the last scs_lin_sys_keep. It must not change the solver’s copy of the solution of its latest solve (see scs_lin_sys_keep).

Parameters:

  • w – Linear system private workspace.

  • b – Right-hand side.

  • x – Point at which the residual is evaluated, or SCS_NULL.

Returns:

\(\|b - K x\|_\infty\), SCS_LIN_SYS_PRODUCTS_NOT_PROVIDED or SCS_LIN_SYS_PRODUCTS_FAILED (see the contract above).

void scs_lin_sys_keep(ScsLinSysWork *w, const scs_float *x)

Stores x as the guess x0 of the next correction-form solve. x is always the solution returned by the latest scs_solve_lin_sys or scs_lin_sys_correct call, unchanged, so a solver that keeps that solution on its side (a GPU solver) may store its own copy and not read x. Between that solve and this call SCS may call scs_lin_sys_residual (with that solution or another vector as x, or with SCS_NULL), but no other solve: the residual must therefore leave the solver’s copy of the solution as it is. Called only if the solver provides the products.

Parameters:

  • w – Linear system private workspace.

  • x – The solution of the latest solve.

scs_int scs_lin_sys_correct(ScsLinSysWork *w, scs_float *x)

Solves in correction form: \(x = x_0 + K^{-1} r\), where r is the residual of the latest scs_lin_sys_residual call, which SCS always makes with x equal to SCS_NULL (so \(r = b - K x_0\)) right before. The result counts as the latest solve for scs_lin_sys_keep. Called only if the solver provides the products.

Parameters:

  • w – Linear system private workspace.

  • x – Output, the solution.

Returns:

status != 0 indicates failure.
